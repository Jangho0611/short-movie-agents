# 대산 Shorts TTS Style Guide

## 1. 목적

대산 Shorts의 TTS를 처음부터 승인 톤에 가깝게 작성하기 위한 입력 규칙이다. 음성 모델을 학습시키는 문서가 아니라, 승인된 1탄의 문장·설정·결과에서 재사용 가능한 작성 원칙을 추출한 것이다.

목표 톤은 **차분한 현장 실무자가 옆에서 짧게 설명하는 말투**다. 정보는 정확하게 유지하되 자막용 문장과 음성용 문장을 분리한다.

## 3. 고정 Voice

- voice: `ko-KR-Chirp3-HD-Alnilam`
- language: `ko-KR`
- audio encoding: `MP3`
- 권장 기본 speakingRate: `1.00`
- pitch: 설정하지 않음(모델 기본값)
- volume gain: 설정하지 않음(모델 기본값)

속도를 문장 문제의 치료제로 사용하지 않는다. 먼저 문장을 고친 뒤 필요할 때만 `0.96~1.02` 범위에서 소폭 비교한다.

## 4. 기본 말투

- 짧고 차분하게 설명한다.
- 현장에서 실제로 쓰는 쉬운 동사를 우선한다.
- 전문 정보는 유지하되 명사를 연속해서 쌓지 않는다.
- 과장하거나 시청자에게 호통치는 말투를 쓰지 않는다.
- 한 Scene에서 핵심 메시지는 하나만 전달한다.

권장:

> 소송각재는 원목이라 휘어지거나 뒤틀리는 정도가 제품마다 다를 수 있습니다.

비권장:

> 소송각재는 원목 기반 자재라 건조 상태 및 목재 특성에 따른 휨·뒤틀림 편차가 발생할 수 있습니다.

## 5. 문장 길이 규칙

- 한 문장은 가급적 15~30자, 최대 약 35자를 목표로 한다.
- 한 호흡이 5초를 크게 넘으면 두 문장으로 나눈다.
- 원인·결과가 모두 길면 각각 한 문장으로 나눈다.
- 자막의 줄바꿈을 그대로 TTS 호흡으로 간주하지 않는다.
- 한 Scene의 spokenText는 1~3개의 짧은 문장으로 구성한다.

1탄 Scene 1의 핵심 교훈은 `휘어진 제품이 너무 많으면 현장에서는`처럼 조건과 결과를 한 호흡으로 잇지 않고, 두 문장으로 분리한 것이다.

## 6. 호흡/쉼표 규칙

- 쉼표는 문법 표시가 아니라 **실제로 짧게 쉴 지점**에만 쓴다.
- 문장당 쉼표는 원칙적으로 0~1개다.
- 조건·전제 뒤에 짧은 쉼이 필요할 때만 사용한다.
- 강한 의미 전환은 쉼표 대신 마침표로 문장을 나눈다.
- 명사 나열마다 쉼표를 넣지 않는다.
- TTS 입력의 줄바꿈에 의존하지 않고 쉼표·마침표로 호흡을 명시한다.

좋음:

> 자재 선택이 고민된다면, 대산이 도와드립니다.

나쁨:

> 소송각재는, 원목 기반이라, 휘어짐이나, 뒤틀림에, 편차가 생길 수 있습니다.

1탄의 `그리고,`는 실제 승인 파일의 개별 호흡 보정 사례다. 이를 모든 접속사 뒤에 적용하는 일반 규칙으로 삼지 않는다.

## 7. captionText / spokenText 분리 규칙

- `captionText`: 화면에서 정확히 보여야 하는 전문용어와 핵심 정보
- `spokenText`: 같은 뜻을 사람이 말하기 쉽게 풀어 쓴 문장
- 두 값의 의미와 결론은 같아야 한다.
- 발음 오류를 피하기 위한 활용형·쉬운 동사·조사 변경은 허용한다.
- 숫자, 규격, 법적 표현처럼 정확성이 중요한 정보는 임의로 풀어 쓰지 않는다.

예:

```text
captionText: 휨이나 뒤틀림 편차
spokenText: 휘어지거나 뒤틀리는 정도의 차이
```

화면 자막을 TTS 발음 때문에 바꾸지 않고, TTS 대본을 자막 가독성 때문에 딱딱하게 만들지 않는다.

## 8. 전문용어 발음 규칙

확정 매핑은 `docs/tts-pronunciation-map.json`을 단일 기준으로 사용한다.

| 용어 | 현재 기준 | 처리 |
|---|---|---|
| 휨 | 발음 문제 확인 | 자막은 `휨`, 음성은 문맥에 따라 `휘어짐` 또는 `휘어지다` 활용 |
| 뒤틀림 | 별도 오류 근거 없음 | 그대로 사용하거나 자연스러운 동사 `뒤틀리다` 사용 |
| 하지재 | 1탄 승인 음성에 사용됨 | `하지재` 유지 |
| 소송각재 | 현재 음성에 사용 중 | 우선 유지, 앞뒤 조사를 붙여 자연스럽게 읽히는지 검수 |
| LVL | 대체 표기 승인 전 | 생성 전 `LVL 각재`처럼 띄고, 필요 시 `엘브이엘` 후보를 별도 검수 |
| 베니어 | 대체 표기 승인 전 | 우선 `베니어` 유지 |
| 공학목재 | 대체 표기 승인 전 | 우선 유지하되 spokenText에서는 `공학 목재` 호흡도 비교 |

확인되지 않은 표기를 발음 사전에 확정 추가하지 않는다. 후보는 생성 후 실제 발음을 듣고 승인된 경우에만 등록한다.

## 9. 영문 약어 읽기 규칙

- 화면에는 업계 표기인 `LVL`을 유지한다.
- TTS 입력에서는 약어와 뒤 단어를 붙여 쓰지 않는다: `LVL각재`보다 `LVL 각재`.
- 모델 발음이 불명확하면 spokenText에서 `엘브이엘`을 후보로 사용한다.
- 한글 음차는 실제 승인 음성을 얻기 전 pronunciation map에 확정하지 않는다.
- 영문 약어가 여러 번 나오면 첫 1회만 풀어 읽고 뒤에서는 자연스러운 짧은 표현을 사용한다.

## 10. 종결어미 규칙

- `~입니다`, `~할 수 있습니다`를 연속해서 반복하지 않는다.
- 설명, 가능성, 권유를 섞는다: `~입니다` / `~다를 수 있습니다` / `~고르세요`.
- 같은 Scene 안에서 모든 문장을 같은 종결어미로 끝내지 않는다.
- 지나친 구어체나 반말은 쓰지 않는다.
- 브랜드 엔딩의 `대산이 도와드립니다`는 1탄 승인 문구이므로 유지한다.

## 11. 금지되는 AI 문체

- 명사를 세 개 이상 연속 나열하는 보고서 문체
- `~하기 위한 구조가 특징입니다` 같은 중복 설명
- `~할 수 있습니다`의 연속 반복
- 쉼표로 모든 구를 잘게 끊는 낭독체
- 한 문장 안에 원인·정의·효과·결론을 모두 넣는 구성
- 과장된 유튜버 말투

금지 표현:

- 여러분!
- 놀랍게도
- 무조건
- 꼭 기억하세요
- 사실은 말이죠
- 완전 다릅니다

## 13. 신규 Shorts TTS 작성 절차

1. 기획 문장에서 Scene별 핵심 메시지를 하나씩 정한다.
2. 정확한 화면용 `captionText`를 작성한다.
3. captionText를 복사하지 말고 말하기 쉬운 `spokenText`를 별도로 작성한다.
4. pronunciation map의 확정 항목만 적용한다.
5. 35자 초과 문장, 명사 나열, 반복 종결어미를 검사한다.
6. 쉼표를 지우고도 자연스러운지 확인한 뒤 필요한 쉼표만 되돌린다.
7. 기본 `speakingRate: 1.00`, pitch 기본값으로 Scene별 1회 생성한다.
8. 발음·호흡·톤을 검수하고 실패 원인을 `문장`, `발음`, `속도`로 구분한다.
9. 문장 문제는 문장으로 고치고, 속도는 마지막에만 소폭 조정한다.

향후 자동화 설계:

```text
기획 문장
→ captionText
→ Style Guide 기반 spokenText 후보
→ pronunciation map 적용
→ 길이/쉼표/종결어미 정적 검사
→ 사용자 승인
→ TTS 1회 생성
→ 음성 검수
```

이번 문서는 설계 기준이며 자동 변환 코드는 아직 구현하지 않는다.

## 17. speakingRate 판단

- 1탄 최종 승인: `1.00`
- 2탄 현재 기본값: `0.89`
- 차이: `-0.11` (1탄보다 11% 낮은 설정값)

0.89는 문어체 문장의 음절과 문장 끝을 더 오래 노출해 느린 AI 낭독 인상을 강화할 수 있다. 1탄 기록에서도 0.89 후보는 자연스럽지 않았고, 최종 승인은 문장 구조를 고친 뒤 1.00에서 이루어졌다.

따라서 앞으로의 기본값은 `1.00`을 권장한다. 다만 현재 Scene 2 v3를 생성하기 전에는 사용자 지시대로 rate를 변경하지 않으며, 먼저 권장 문구를 확정해야 한다.
