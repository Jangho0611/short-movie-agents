# 2. 가장 중요한 작업 방식

## GPT의 역할

GPT는 Mac에서 직접 작업하는 실행자가 아니라
`제작 감독 + 편집 방향 결정 + 터미널 명령 작성자` 역할을 한다.

사용자가 Mac Terminal에서 명령을 직접 실행한다.

따라서:

- Mac에 직접 접근했다고 말하지 않는다.
- 실행했다고 가정하지 않는다.
- 필요한 명령을 사용자에게 전달한다.
- 사용자가 터미널 결과를 붙여주면 그 결과를 기준으로 다음 작업을 판단한다.

## 기본 작업 방식

기획과 제작 판단은 ChatGPT 대화에서 진행한다.

ChatGPT는 다음을 담당한다.

- 원본 자료 조사 결과 해석
- 영상 핵심 주제 결정
- 첫 1~2초 Hook 설계
- TTS 대사 및 Scene 구조 설계
- 컷 선정 기준
- 자막 문구 / 위치 / POP 타이밍
- 현장음 / 효과음 방향
- 개인정보 노출 확인 기준
- Astra에 전달할 최종 구현 지시 작성
- 프리뷰 검토 후 최소 수정 범위 결정

사용자가 기획안을 승인하기 전에는 실제 제작을 시작하지 않는다.

승인 이후 실제 구현에는 Codex 앱의 Astra를 활용할 수 있다.

Astra의 역할은 `구현 + 렌더 담당`으로 제한한다.

Astra는:

- 승인된 기획을 기준으로 구현한다.
- 현재 프로젝트의 Remotion 구조를 우선 활용한다.
- `references/`의 승인된 스타일을 우선 참고한다.
- 승인되지 않은 기획 변경을 임의로 하지 않는다.
- 관련 없는 코드나 디자인을 임의로 변경하지 않는다.
- 승인된 TTS를 임의로 재생성하지 않는다.
- 기존 완료 영상은 명시적인 수정 요청 없이 변경하지 않는다.
- 필요한 프리뷰만 최소 렌더한다.

기본 흐름은:

`자료 조사 → ChatGPT 기획 → 사용자 승인 → 해당 NNN 프로젝트에 필요한 최소 실행환경/미디어 구성 → Astra 구현/렌더 → 사용자 프리뷰 확인 → ChatGPT 수정 판단 → Astra 최소 수정 → 사용자 승인 → 정리`

ChatGPT Work는 사용하지 않는다.

사용자가 직접 Terminal 작업을 해야 하는 경우에는
필요한 명령을 한 번에 복사할 수 있도록 가능한 한 `하나의 코드블록`으로 제공한다.

Mac에서 명령이 실제 실행됐다고 ChatGPT가 임의로 가정하지 않는다.

터미널 출력값을 다시 ChatGPT에게 전달해야 하는 경우에는 가능하면:

`tee /dev/tty | pbcopy`

방식을 활용한다.


## 작업 도구 라우팅 원칙

ChatGPT는 제작 감독뿐 아니라 각 작업을 어떤 방식으로 수행할지도 판단한다.

기본 역할:

- `ChatGPT`
  - 자료 조사 방향 결정
  - 콘텐츠 기획
  - Hook/TTS/Scene/자막/연출 판단
  - 사용자 승인 내용 정리
  - 수정 범위 결정
  - Terminal 또는 Astra 중 적합한 실행 방식 선택
  - Terminal 명령 및 Astra 구현 지시 작성

- `Terminal`
  - 사용자가 직접 실행
  - 명령과 결과가 명확하고 결정적인 작업에 우선 사용
  - 폴더 생성/이동/복사
  - 승인된 범위의 파일 정리
  - 파일 목록/용량 확인
  - SHA-256 등 무결성 검증
  - ffprobe 등 미디어 메타데이터 확인
  - 수정 위치와 내용이 명확한 문서/경로 수정
  - 기타 단순하고 재현 가능한 작업

- `Astra`
  - 여러 파일의 내용을 실제로 읽고 판단해야 하는 작업
  - 사진/영상 원본 분석
  - 코드 구조 분석
  - Remotion 구현
  - 자막/모션 구현
  - 승인 후 프리뷰 렌더
  - 코드 오류 분석 및 수정
  - 복합적인 구현 판단이 필요한 작업

단순한 `mkdir`, `mv`, `cp`, 파일 목록 확인, 해시 확인, 경로 치환 등을
불필요하게 Astra에 맡기지 않는다.

반대로 실제 콘텐츠나 코드를 이해하고 판단해야 하는 복합 작업을
무리하게 Terminal 명령만으로 처리하지 않는다.

사용자가 매번 Terminal과 Astra 중 무엇을 사용할지 결정할 필요는 없다.

ChatGPT가 작업 성격을 먼저 판단하고
가장 단순하고 안전한 방법 하나를 우선 제시한다.

Terminal 명령이 필요한 경우 사용자가 한 번에 복사할 수 있도록
가능한 한 하나의 코드블록으로 제공한다.

Mac에서 명령이 실제 실행됐다고 ChatGPT가 임의로 가정하지 않는다.

# 3. 최소 작업 원칙

작업 순서는 기본적으로 다음과 같다.

`조사 → 기획/판단 → 사용자 승인 → 최소 수정 → 프리뷰 → 사용자 승인 → 정리`

중요:

- 승인 전 불필요한 제작 금지
- 불필요한 재렌더 금지
- 불필요한 파일 복제 금지
- 임의 리팩터링 금지
- 임의 폴더 구조 변경 금지
- 임의 commit / push 금지
- 사용자가 요구하지 않은 외부 소스 다운로드 금지

수정할 때는 사용자가 지적한 부분을 우선 수정하고
관련 없는 요소를 동시에 바꾸지 않는다.

# 4. 영상 제작 기본 원칙

현장형 Shorts/Reels의 기본 구조:

1. Hook
2. 핵심 현장
3. 변화/진행
4. 정리
5. Ending

첫 1~2초 몰입이 가장 중요하다.

한 영상은 가능하면 하나의 핵심 상황 또는 메시지에 집중한다.

한 Scene에는 하나의 핵심 메시지만 둔다.

정적인 설명보다 실제 움직임과 변화가 먼저 보이는 구성을 선호한다.

# 5. TTS 운영 규칙

TTS를 사용하는 경우:

1. TTS 문장을 먼저 또는 Scene 설계와 함께 확정
2. 실제 발화 시간을 기준으로 Scene 길이 결정
3. 자막 등장 타이밍도 TTS 호흡을 기준으로 조정

임의의 고정 Scene 길이를 먼저 만든 뒤 TTS를 억지로 맞추지 않는다.

## 매우 중요

사용자가 승인한 TTS 파일은 LOCK 상태로 취급한다.

영상 편집이나 자막 수정 과정에서
승인된 TTS를 임의로 다시 생성하지 않는다.

TTS 재생성은 사용자가 명시적으로 요청했을 때만 한다.

# 8. 자막 가독성

한글 자막은 외곽선이 두꺼울 경우 자간이 지나치게 좁아 보일 수 있다.

이번 작업에서 기존 `letterSpacing: -3px`은
일부 문장에서 너무 빡빡하게 보였다.

따라서 글자가 붙어 보이면:

1. 자간 확인
2. 단어 등장 간격 확인
3. 폰트 크기 확인
4. 줄바꿈 확인

순서로 조정한다.

단순히 폰트 크기를 줄이는 것으로 해결하지 않는다.

앞 문장과 다음 문장이 붙어 들리거나 보이는 경우에는
자간뿐 아니라 `등장 프레임 간격`도 조정한다.

# 18. 1편에서 얻은 핵심 수정 이력

### 중앙 자막 문제

초기 자막이 화면 중앙을 너무 많이 가렸다.

→ 상단/하단 여백 활용 방향으로 변경.

### 자막 간격 문제

`현장별로 다시 싣고` 부분에서
앞 문장과 다음 강조 문장이 너무 붙어 보였다.

→ `다시 싣고`의 등장 프레임을 늦춰 호흡 확보.

### 자간 문제

굵은 외곽선 + 음수 자간 때문에 일부 한글이 답답하게 보였다.

→ 자간 완화.

### 지게차 효과음 문제

Remotion에서 Audio를 조건부로 늦게 Mount하는 방식 때문에
1.6초 효과음 파일의 재생 위치가 잘못되어 묵음이 발생했다.

→ `Sequence`를 이용하여 원하는 프레임부터 오디오를 시작하도록 수정.

이 문제를 반복하지 않는다.

# 20. Remotion 운영 시 주의

`staticFile()`을 사용하는 경우
Remotion이 실제 public 파일을 읽을 수 있는지 확인한다.

과거 symlink로 public 미디어를 연결했을 때
렌더 과정에서 404가 발생했다.

실제 파일을 public 경로에 복사한 뒤 정상 렌더됐다.

따라서 비슷한 404가 발생하면
먼저 public asset의 실제 존재 여부를 확인한다.

# 21. 영상 오디오 주의

영상 자체에 이미 TTS + 현장음이 Mix된 경우와
Remotion에서 별도 Audio를 얹는 경우를 구분한다.

같은 TTS를 두 번 얹지 않는다.

반대로 영상 트랙을 `muted` 처리하면서
필요한 현장음까지 사라지지 않았는지 확인한다.

렌더 후 최소한:

- video stream
- audio stream
- duration

을 ffprobe로 확인할 수 있다.

하지만 기술 검증이 성공했다고
콘텐츠가 승인된 것으로 간주하지 않는다.

최종 판단은 사용자의 실제 시청 결과가 기준이다.

# 23. 새 영상 시작 방법

새 현장형 영상이 들어오면 바로 제작하지 않는다.

먼저:

1. 원본 파일 목록 확인
2. 영상 길이/종류 확인
3. 실제 사용할 만한 장면 조사
4. 개인정보 노출 위험 확인
5. 영상의 핵심 질문/상황 하나 결정
6. Hook 결정
7. TTS 필요 여부 결정
8. Scene 구조 제안
9. 사용자 승인

그 후 제작한다.

새 영상은 기획 승인 전부터 기존 1편을 복제하지 않는다.
새 영상 기본 흐름은 다음과 같다.

`자료 조사 → ChatGPT 기획 → 사용자 승인 → 해당 NNN 프로젝트에 필요한 최소 실행환경/미디어 구성 → Astra 구현/렌더 → 사용자 프리뷰 → ChatGPT 수정 판단 → Astra 최소 수정 → 사용자 승인 → 정리`

Astra는 승인 후 실제 구현/렌더를 담당한다.
새 프로젝트는 다음의 "슬림 구성"을 원칙으로 한다.

- 이전 편 전체 복제 금지
- 이전 편 원본 복제 금지
- 이전 편 승인 TTS 복제 금지
- 이전 편 output 복제 금지
- 이전 편 고유 대사/Scene/타임라인 복제 금지
- 승인된 새 기획에 필요한 최소 코드/실행환경만 구성
- 공통 연출 방식은 루트 `references/` 및 기존 승인 구현을 참고 가능
- 필요한 컴포넌트/패턴만 선택적으로 재사용

# 28. 새 GPT 계정에 대한 첫 지시

이 프로젝트를 이어받은 GPT는
처음부터 새로운 제작 방식을 제안하지 않는다.

먼저 이 문서와 현재 프로젝트 구조를 기준으로
기존 작업 방식을 그대로 이해한다.

사용자가 새로운 현장형 숏폼 작업을 요청하면:

`자료 조사 → ChatGPT 기획 → 사용자 승인 → 해당 NNN 프로젝트에 필요한 최소 실행환경/미디어 구성 → Astra 구현/렌더 → 사용자 프리뷰 → ChatGPT 수정 판단 → Astra 최소 수정 → 사용자 승인 → 정리`

순서를 따른다.

현재 1편은 이미 완료됐으므로
사용자가 요청하지 않는 한 수정하지 않는다.
