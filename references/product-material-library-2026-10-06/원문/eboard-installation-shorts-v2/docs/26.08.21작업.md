# 이보드 Shorts 2탄 작업 기록 — 2026-08-21

## 프로젝트 목적

- 1탄은 `이보드가 어떤 자재인가?`를 설명한다: 특징, 구조, 종류, 기본 활용 정보.
- 2탄은 셀프인테리어 사용자가 참고할 수 있도록 `이보드는 실제로 어떻게 시공하는가?`를 다루는 짧은 실사형 시공 튜토리얼이다.
- 대상은 이보드 구매 고려자, 셀프인테리어 사용자, 시공 과정을 알고 싶은 일반 고객이다.
- Visual Tone은 과장된 광고가 아닌 `실사형 국내 인테리어 현장`이다.

## 전체 Scene 기획 초안

1. S1 — 시공 시작 Hook: 작업자가 이보드를 벽 앞으로 가져와 시공 직전 위치를 맞춘다.
2. S2 — 바탕면 확인/준비. 구체 방법은 제조사 자료 검증 전 미확정.
3. S3 — 치수 확인 및 이보드 재단. 공구·절차는 검증 전 미확정.
4. S4 — 벽체 부착. 접착제 종류와 도포법은 검증 전 미확정.
5. S5 — 이음부 및 마감 전 처리. 처리법은 검증 전 미확정.
6. S6 — 도배/페인트 등 최종 마감 연결. 적용 가능 방식은 검증 전 미확정.
7. S7 — 핵심 주의사항 정리. 제조사 권장 방식 확인 후 확정.
8. S8 — DAESAN Ending.

S4~S7은 기획 초안만 기록했으며 실제 Scene, TTS, Remotion은 아직 제작하지 않았다.

## 제작 방식 및 초기 검증 기록

- deterministic 합성만으로는 작업자·국내 실내 현장·벽·정확한 제품을 자연스럽게 한 장면에 구성할 승인 자산이 부족하다고 판정했다.
- Start Frame은 Vertex AI 이미지 파이프라인(`gemini-3.1-flash-image`)으로 단일 후보씩 검증했다. 초기 후보는 제품 비율 문제로 사용하지 않는다.
- Start Frame QA: 국내 실내 공사 현장, 작업자 한 명, 벽체 원근, 손과 그립, 텍스트·가짜 로고 부재는 PASS. 검은 표면과 얇은 분홍색 코어는 유지됐으나 판재가 canonical reference의 정규 대형 판재 비율보다 짧게 표현되어 제품 비율 항목은 FAIL/사용자 확인 필요로 판정했다.
- 초기 Flow는 제품 정확도 문제가 있으면 진행하지 않는 원칙에 따라 보류했다.
- Scene 1 TTS는 시각 방향 검증에 필수적이지 않아 생성하지 않는다. 추후 동일 화자 `ko-KR-Chirp3-HD-Alnilam` 유지 예정.
- 전체 TTS, 전체 Remotion, Cover, final은 미제작이다.

## 실패 테스트와 재발 방지

- 제품 reference는 전체판 canonical 이미지를 우선해 대형 장방형 비율, 검은 표면, 얇은 분홍 XPS 코어를 잠근다.
- 한 프레임에 측정과 재단을 함께 넣지 않고 Scene의 핵심 동작 하나만 명확히 표현한다.
- 생성 영상에서 안전자 이동과 불필요한 후속 동작이 반복됐다. 짧은 Veo 영상은 `핵심 동작 → 결과 상태 hold → 종료`로 설계하고 중요한 동작이 마지막 프레임과 동시에 끝나지 않게 한다.
- 실제 사용시간에 가까운 최소 길이를 우선하며 불필요한 앞 동작을 최소화한다.
- Vertex/Veo에 실제 전달하는 생성 프롬프트는 영어로 작성한다.
- 생성 결과 후반에 drift가 있으면 승인 원본을 덮어쓰지 않고 안정 구간 직전에서 Remotion trim한다.

## 프로젝트 운영 규칙

- 프로젝트 시작 시 필요한 코드·설정·lockfile·canonical 자산만 가져오는 슬림 복사를 적용한다. `node_modules`는 복사하지 않고 lockfile 기준으로 재설치한다.
- Scene reference는 과도한 하위 폴더를 만들지 않고 `public/references/` flat 구조에 Scene 번호와 역할이 드러나는 파일명으로 보존한다.
- 사용자 최종 확인용 Scene 단독 preview도 `public/references/`에 보존한다. `tmp/`는 contact sheet 등 일회성 QA 또는 폐기 예정 파일에만 사용한다.
- Vertex 이미지 생성은 최종 후보 파일 1개만 직접 저장한다. `*-vertex-vN.png` 같은 원본·규격화본 이중 저장은 금지하며, 기존 중복 파일은 이번 작업에서 정리하지 않는다.
- canonical 제품 reference는 `public/references/products/`에서 별도로 구분한다.
- 기존 이보드 1탄 프로젝트는 수정하지 않는다.
- 실패·구버전 파일은 참조 여부를 확인한 뒤 영구삭제하지 않고 macOS 휴지통으로 이동한다.
- 오늘은 Git 작업, 신규 생성/API 호출, TTS, S4 이후 제작을 하지 않는다.
