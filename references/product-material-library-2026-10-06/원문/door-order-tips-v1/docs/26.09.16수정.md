## 5. Cover 제작 과정 및 실패 회복

- 캐릭터 투명화: "이미 투명"으로 가정한 `-alpha-v1` 파일이 실제로는 불투명(alpha=255)이었음을 픽셀 검사로 발견 → border flood-fill 대신 **전역 near-white 임계값** 방식(`global-white-transparent.js`)으로 전환, 다리 사이 흰 배경까지 정상 제거
- 그림자 제거: 흰색이 아닌 연회색 그림자는 별도 밝기/채도 기준 pass 필요(`remove-shadow2.js`, threshold 2회 조정)
- 로고 합성 버그: `sharp().composite()`에 `width/height`를 직접 넣으면 리사이즈가 무시되고 원본 크기로 깨짐 → 레이어별 `.resize().toBuffer()` 사전 처리로 해결
- 타이포/박스 스타일: 방염 시리즈 §23 네이비 박스 템플릿을 그대로 적용했다가 반려 → **DESIGN_Figma.md** 재확인 후 pastel `block-mint` 컬러블록 + 검정 텍스트(그림자 없음, `rounded.xl` 32px)로 전환해 최종 승인
- 최종 승인: `door-order-cover-v13.png` (Main DESIGN: Figma)

## 6. 정리 과정 실수 및 복구 (중요 재발 방지 기록)

Scene별 QA 프레임 스냅샷(`scene0X-frameNNN-vN.png`)을 전부 "중간 임시파일"로 판단해 일괄 삭제했는데, 각 Scene의 최신 버전이 사실상 "최종 확정 프레임"이었음을 나중에 지적받음. `rm -f`로 지워 git 커밋 전이라 히스토리 복구 불가 확인. 승인된 `door-order-full-v6.mp4`에서 Scene duration 상수 기준으로 동일 상대 위치 프레임을 재추출해 `*-FINAL.png`로 복구(완전히 동일하지 않을 수 있음, 원본 개발 중 버전과는 다를 수 있음).

**재발 방지**: 여러 버전이 쌓인 QA 자산을 정리할 때는 "전부 임시파일"로 일괄 판단하지 않고, 버전 중 최신/최종에 해당하는 것은 별도로 분리해 보존 여부를 먼저 확인한다.

## 7. 다음 프로젝트 재사용 규칙 vs 이번 품목 고유 규칙

**공통 규칙(재사용)**
- 캐릭터 투명화는 border flood-fill이 아닌 전역 near-white 임계값 방식 사용
- 그림자 제거는 밝기/채도 기준 별도 pass 필요
- `sharp().composite()` 레이어는 항상 사전 `.resize().toBuffer()` 후 전달
- Cover 박스/타이포 스타일은 실제 DESIGN.md 원문을 직접 재확인 후 적용(다른 시리즈 템플릿을 그대로 재사용하지 않는다)
- SNS copy는 반드시 `SNS_업로드_문구_가이드.md`의 각 편 템플릿(구분선이 홍보문구 앞뒤를 감싸는 구조, `daesan.ai` plain 표기)을 그대로 따른다
- 해시태그는 핵심 키워드 외에 브랜드/대리점/가격/견적 등 롱테일 키워드를 다양하게 섞는다
- 새 프로젝트 슬림카피 시 다른 프로젝트 파일(MdfGradeFull 등)이 섞여 들어가지 않았는지 Root.tsx까지 확인한다
- 버전이 여러 개 쌓인 QA 자산 정리 시 최신/최종본은 별도로 분리해 보존 여부를 먼저 확인한다

**이번 품목(도어) 고유 규칙**
- 도어 발주 4대 체크포인트: 바닥재별 하부 여유값, 대리석 하부식기 옵션, 손잡이 타공 위치, 문짝로고 유무
- Scene05 로고 비교: 더도어(보급형, 로고 있음) vs 영림도어(고급형, 로고 없음)
- 캐릭터 영상(`daesan-motion-v1.mp4`)을 Scene01/06에서 공용
