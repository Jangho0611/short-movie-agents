- Flow 원본 영상은 720×1280, 24fps다.

- Scene 1/2 연결 테스트는 FFmpeg concat demuxer와 `-c copy`로 정상 재생을 확인했다.

- Scene 1/2/3/5는 Flow 원본 모션과 playbackRate를 유지했다.

## 주요 시행착오와 최종 판단

### Google Flow 실사 영상 제작

- 시도: Scene 1~3과 Scene 5를 실제 석고보드 시공 현장처럼 보이도록 Google Flow로 제작했다. 벽체 설명, 석고보드 위치 잡기, 타카 고정, 완성 벽에서 내부 하지 구조가 드러나는 흐름을 각각 실사 모션으로 테스트했다. 특히 타카 작업은 정지 이미지 기반 연출을 보완하기 위해 Flow 영상으로 다시 제작했다.
- 문제: 생성 시도마다 작업자의 외형, 복장과 동작이 완전히 동일하게 이어지기 어려웠고 타카 작업은 공구와 손동작이 자연스럽게 보이는 결과를 얻기까지 시행착오가 있었다.
- 원인 판단: 생성형 영상은 Scene별로 독립 생성되므로 동일 작업자와 복장의 연속성을 완벽하게 고정하기 어렵고, 손과 공구가 맞닿는 짧고 정밀한 시공 동작은 생성 난도가 높다고 판단했다.
- 해결: 각 Scene의 핵심 시공 의미가 분명한 결과를 우선 선별하고, 장면 순서와 설명 TTS·자막으로 전체 작업 흐름을 연결했다. 타카 장면은 여러 정지 이미지 모션 시도 대신 실제 동작이 포함된 Flow 결과를 사용했다.
- 최종 채택: Scene 1, 2, 3, 5는 최종 선별한 Flow 원본 MP4를 사용하고, 작업자 연속성보다 시공 단계의 명확성과 실제 모션의 자연스러움을 우선했다.

### Flow 영상의 Remotion 재렌더 문제

- 시도: Flow 원본을 Remotion 안에서 합성해 렌더했으며 30fps와 원본 기준 24fps 렌더를 비교했다. CFR 여부, 프레임 수와 타임스탬프를 확인하고 1080×1920 업스케일, 높은 비트레이트, `yuvj420p` 색 처리 차이도 분석했다. 이후 원본과 같은 720×1280, 24fps, 낮은 비트레이트 조건의 경량 렌더도 시험했다.
- 문제: 원본과 렌더의 프레임은 거의 1:1로 유지됐지만 Remotion 재렌더본은 QuickTime과 브라우저 재생에서 Flow 원본보다 체감상 끊겨 보였다.
- 원인 판단: 단순한 24→30fps 변환이나 비정상 타임스탬프가 원인은 아니었다. 1080 업스케일, 높은 비트레이트와 색 처리 부담은 재생 부하를 키우는 요인이었으나, 경량 조건에서도 원본과 같은 체감 부드러움을 안정적으로 재현하지 못해 Flow 영상의 재인코딩 자체를 피하는 편이 안전하다고 판단했다.
- 해결: Scene 1/2를 FFmpeg concat demuxer와 `-c copy`로 직접 연결해 원본 스트림 재생이 자연스러운지 확인했다. 이후 Flow Scene 1/2/3/5는 Remotion에 넣지 않고 원본 MP4를 사용하며, 필요한 TTS·자막과 다른 Scene을 FFmpeg 중심으로 최종 합성했다.
- 최종 채택: Flow 원본 MP4 직접 사용, 24fps 유지, FFmpeg 중심 조립 방식을 채택했다. Remotion 재렌더는 Flow 원본 Scene에 사용하지 않는다.

### Scene 3 타카 Remotion 모션 테스트

- 시도: 타카 정지 이미지에 공구 진동과 recoil을 주는 방식, 발사 순간 벽 방향으로 1~2px 눌렀다가 복귀하는 최소 모션, 발사 위치 이동과 고정점 표현을 시험했다. 짧고 건조한 타카·에어 스테이플러 SFX를 세 번 동기화하는 방식과 완전 정지 이미지에 SFX만 사용하는 방식도 테스트했다.
- 문제: 공구만 자연스럽게 분리해 움직일 수 없는 단일 이미지여서 타카총 자체가 흔들리거나 작업자와 공구가 함께 진동하는 인상이 생겼다. 미세 모션도 실제 발사보다 이미지 전체의 인위적인 움직임으로 보였고, SFX만으로는 시각적 시공 동작의 부족을 해결하지 못했다.
- 원인 판단: 한 장의 실사 이미지는 손, 공구, 작업자 몸과 배경이 한 평면에 묶여 있어 실제 관절·접촉 동작과 원근 변화를 재현하는 데 한계가 있다고 판단했다.
- 해결: recoil, 진동, 눌림, 고정점, zoom/pan을 차례로 제거하고 정지 설명 컷까지 검토한 뒤, 실제 타카 시공 모션이 포함된 Flow 영상을 최종 Scene 3으로 선택했다.
- 최종 채택: Scene 3은 `scene03-flow-v1.mp4`를 사용한다. Remotion 타카 모션과 타카 SFX 테스트는 최종본에서 제외했다.

### Scene 4 Remotion reveal

- 시도: 시공 전후를 보여주는 `scene05-start-v1.png`와 `scene05-end-v1.png`를 같은 구도로 겹치고, dissolve/crossfade와 좌→우 reveal을 검토했다.
- 문제: 단순 crossfade는 인물이나 구조물 경계가 동시에 겹쳐 보이는 고스팅을 만들 수 있고, 실제 석고보드가 추가 시공되는 방향성이 약했다.
- 원인 판단: 두 이미지의 공통 구도를 유지하면서 시공 결과만 순차적으로 보여주려면 전체 투명도를 섞는 방식보다 완성 이미지를 한 방향으로 드러내는 마스크가 적합하다고 판단했다.
- 해결: start 이미지를 아래에 두고 end 이미지를 위에서 좌→우로 드러내는 mask wipe를 적용했다. 속도는 약한 ease-in-out 흐름으로 유지하고 zoom, pan, 왜곡과 추가 그래픽을 넣지 않았다.
- 최종 채택: 720×1280, 24fps, 4초의 `scene04-remotion-v1.mp4`를 사용한다. Scene 4의 최종 전환은 crossfade가 아닌 좌→우 mask reveal이다.

### Scene 5 Flow 내부 구조 연출

- 시도: 완성된 벽면에서 안쪽의 목재 하지 구조가 보이는 흐름을 Flow 실사 영상으로 구성하고, 약 4초와 6초 길이에서 설명 전달력과 TTS 수용 가능 시간을 비교했다.
- 문제: 4초 구간은 완성 벽과 내부 구조의 관계를 보여주고 설명 문장을 자연스럽게 넣기에 짧았다. 초기 긴 TTS 문구는 6초도 초과해 문구를 여러 번 줄여야 했다.
- 원인 판단: 내부 구조 reveal을 인지할 시각적 시간과 자연스러운 발화 시간을 함께 확보해야 하며, playbackRate를 바꾸거나 발화를 빠르게 만드는 방식은 Flow 모션과 설명 품질을 해친다고 판단했다.
- 해결: Flow 원본 6초를 유지하고 TTS를 `겉은 평범한 벽처럼 보여도 안쪽에는 하지 구조가 숨어 있습니다.`로 단축해 5.184초에 맞췄다.
- 최종 채택: Scene 5는 6초의 `scene05-flow-v1.mp4`와 5.184초 최종 TTS를 사용한다.

### TTS 시행착오

- 시도: `ko-KR-Chirp3-HD-Alnilam`, speakingRate 0.89를 기준으로 쉼표와 마침표를 이용한 호흡 조절, 의미 단위별 segment 생성 후 실제 silence 삽입, Scene별 단일 요청 생성 방식을 차례로 시험했다.
- 문제: 쉼표를 늘려도 의도한 pause가 안정적으로 생기지 않았고, segment를 따로 생성해 합치면 구간마다 톤과 속도감이 달라져 한 문장처럼 들리지 않았다. 모든 문장을 `~합니다/~됩니다`로 끝내자 AI식 설명 말투가 강해졌으며 긴 문장은 Scene 길이를 초과했다.
- 원인 판단: 자연스러운 호흡은 후처리 silence보다 문장 자체의 길이와 의미 구조에 더 크게 좌우되고, 각 요청의 음성 억양이 독립적으로 생성되므로 segment 합성은 일관성을 해칠 수 있다고 판단했다.
- 해결: Scene별 TTS를 한 번에 생성하고 강제 silence를 사용하지 않았다. 문장을 짧게 만들고 `~죠`, `~고요`, `~돼요`, `~습니다` 등 종결어미를 섞어 자연스러운 설명 말투로 정리했다.
- 최종 채택: Scene 1 `우리가 보는 이 벽. 사실 안쪽부터 만들어집니다. 하지 구조를 세운 뒤 석고보드를 붙이는 순서죠.` 8.352초, Scene 2 `하지 구조에 맞춰 석고보드 자리를 잡아주고요.` 3.984초, Scene 3 `위치가 잡히면 타카로 하지재에 단단히 고정해 줍니다.` 4.176초, Scene 4 `붙이다 보면 벽면이 완성돼요.` 3.024초, Scene 5 `겉은 평범한 벽처럼 보여도 안쪽에는 하지 구조가 숨어 있습니다.` 5.184초, Scene 6 `자재 선택이 고민된다면, 대산이 도와드립니다.` 3.552초를 사용한다.

### Flow AI 로고 처리 테스트

- 시도: Scene 1 우하단 AI 로고에 대해 약 104% 확대 crop, 작은 `DAESAN`/`daesan.ai` 브랜드 overlay, 원본을 96~97% 축소해 여백 안에 배치하는 layout 방식을 비교했다.
- 문제: crop은 작업자와 주요 시공 영역의 구도 손실 가능성이 있었고, 브랜드 overlay는 작은 요소라도 로고를 가리기 위한 배너처럼 보일 수 있었다. 축소 layout은 원본을 가리지는 않지만 전체 영상에 별도 프레임 디자인을 적용해야 해 Flow 원본 구도와 다른 Scene의 일관성을 바꿨다.
- 원인 판단: 로고를 숨기기 위한 후처리가 원본 시공 화면보다 더 눈에 띄거나 전체 구도·디자인을 손상할 수 있다고 판단했다.
- 해결: blur, 인페인팅과 삭제 방식은 사용하지 않았고 세 가지 테스트 모두 최종본에서 제외했다.
- 최종 채택: crop, overlay, 축소 layout 없이 Flow 원본 화면을 그대로 유지한다.

### 화질과 FPS 테스트

- 시도: Flow 원본 720×1280, 24fps를 기준으로 1080×1920 Remotion 렌더와 최종본의 Lanczos 1080p 업스케일을 비교하고, 24fps와 30fps 처리 가능성을 검토했다.
- 문제: Remotion 1080 렌더는 높은 비트레이트와 색 처리 부담이 더해졌고 체감 끊김 문제가 있었다. 1080p 업스케일은 출력 규격은 커지지만 원본에 없던 실제 디테일을 만들지는 못했으며 720p와 체감 차이도 크지 않았다.
- 원인 판단: 원본 모션이 이미 24fps이므로 단순 30fps 변환은 새 동작 정보를 만들지 못하고 중복 프레임이나 불필요한 처리만 늘릴 수 있다고 판단했다. 프레임 보간도 원본 모션 보존 원칙에 맞지 않았다.
- 해결: 최종 편집 기준을 24fps로 고정했다. 배포용 1080p는 최종 720p 파일에 Lanczos scale만 적용하고 프레임 보간, 과한 sharpen과 타이밍 변경을 사용하지 않았다.
- 최종 채택: 기준 최종본은 720×1280, 24fps이며 업로드용으로 1080×1920, 24fps Lanczos 업스케일본을 함께 보관한다. 30fps 단순 변환은 사용하지 않는다.

### 프로젝트 용량 정리

- 시도: 최종본 검수 후 preview v1~v7, 레이아웃·AI 로고·Remotion 모션·transition 테스트, 실패·미사용 TTS, 중간 segment, SFX, 미사용 reference와 중복 파일을 분류했다.
- 문제: 반복 테스트로 영상과 오디오 파일이 누적됐고, 이름이 비슷한 파일 중 최종 사용본을 잘못 삭제할 위험이 있었다.
- 원인 판단: 확정 Scene, 확정 TTS, 실제 reference와 재현 소스를 먼저 명시적으로 보존한 뒤 나머지를 정리해야 안전하다고 판단했다.
- 해결: 삭제 전 파일 유형, 경로, 심볼릭 링크 여부와 총 용량을 검증하고 최종 사용 파일을 제외한 69개 파일만 삭제했다.
- 최종 채택: 121,816,112바이트(116.17MiB)를 절약했으며 최종 720p/1080p 영상, Scene 1~6 영상, TTS 6개, 실제 reference 2장, 로고, Remotion/FFmpeg 소스와 실행 설정만 보관한다.

### 프로젝트 복사 운영 규칙

- 시도: 기존 프로젝트 전체를 복사하는 방식과 실행에 필요한 최소 뼈대만 가져오는 방식을 비교했다.
- 문제: 전체 복사는 `node_modules`, `.git`, 기존 대용량 영상·오디오·reference, preview와 cache/temp까지 따라와 새 프로젝트의 용량과 파일 혼선을 키웠다.
- 원인 판단: 의존성은 다시 설치할 수 있고 기존 프로젝트의 이력·결과물은 새 작업에 필요하지 않으므로, 실제로 재사용할 소스와 설정만 선별하는 편이 안전하다고 판단했다.
- 해결: 소스, 설정, 필요한 스크립트와 실제 사용할 자산만 복사하고 생성물·캐시·저장소 메타데이터는 제외하는 규칙을 세웠다.
- 최종 채택: 최소 실행 뼈대만 복사하며 `node_modules`, `.git`, 기존 대용량 영상·오디오·reference 전체, preview, cache, temp는 제외한다. 작업기록은 항상 `docs/YY.MM.DD수정.md`에 남긴다.

## 다음 작업자가 알아야 할 최종 원칙

- Flow 영상은 가능하면 원본 MP4 그대로 사용한다.
- Flow 원본을 Remotion으로 재렌더하지 않는다.
- Remotion은 이미지 기반 Scene, 자막, 엔딩 등 필요한 구간에만 사용한다.
- 최종 조립은 FFmpeg 중심으로 진행한다.
- TTS는 후처리 pause보다 문장 길이와 자연스러운 종결어미를 먼저 설계한다.
- 이미지에 억지 모션을 주기보다 실제 영상과 정지 설명 컷을 구분해 사용한다.
- 최종 확정 후 테스트, 실패, 중간 파일은 보관 기준을 확인한 뒤 정리한다.
