# 대산 건축자재 Shorts/Reels/Naver Clip 제작 지침어 (통합본)

- 버전: `v2.5` (Claude 세션에서 여러 영상 제작 경험을 통합 작성, ChatGPT 프로젝트 이관용)
- 작성 기준일: `2026-09-18`
- `Shorts_제작_운영가이드.md`는 기존부터 사용해온 대산 Shorts의 기본 제작·운영 상세 가이드다. 이 문서는 운영가이드를 대체하지 않으며, 공통 가이드의 핵심 규칙을 요약하고 최근 사용자 승인으로 확정된 실행 방식·우선순위·보완 규칙을 추가하는 실행 지침이다. 일반 Shorts 작업에서는 두 문서를 기본 세트로 함께 적용하며, 이 문서에 요약되지 않은 운영가이드의 상세 규칙도 계속 유효하다.

## 0. 기본 운영 방식

- 영상 1편당 새 채팅(프로젝트) 1개로 진행한다. 각 채팅은 해당 영상의 기획→조사→제작→수정→승인→정리까지만 담당한다.
- 영상별 작업기록 MD는 `Shorts_제작_운영가이드.md` §20에 따라 `YY.MM.DD수정.md` 형식(예: `docs/26.09.18수정.md`)으로 해당 영상 프로젝트에서만 관리한다. `YY.MM.DD작업기록.md`는 대체 표준으로 허용하지 않는다. 영상별 작업기록은 프로젝트 공통 소스에 넣지 않으며 일반 ChatGPT 프로젝트 공통 소스 재업로드 대상에서도 제외한다.
- 공통 규칙으로 확정된 내용만 이 지침어(및 원본 상세 가이드)에 반영한다. 확정되지 않은 1회성 실험은 개별 작업기록에만 남긴다.
- 판단 우선순위: ①사용자의 최신 승인·지시 → ②해당 영상의 최신 작업기록 MD → ③이 지침어 및 원본 공통 가이드 → ④최근 승인된 유사 영상 → ⑤과거 작업기록 → ⑥추론. ③의 동일 항목이 충돌하면 이 지침어에서 명시적으로 변경된 최신 규칙을 우선하고, 충돌하지 않는 `Shorts_제작_운영가이드.md`의 상세 규칙은 그대로 적용한다. 요약에서 생략됐다는 이유로 기존 규칙을 폐기하지 않는다.
- 작업 시작 시 이 실행 지침만 단독 기준으로 삼지 않고, 기본 세트인 운영가이드의 해당 작업 관련 상세 절차도 확인·적용한다. 작업 성격에 따라 AI 이미지/제품 표현은 `건축자재_AI이미지_품목별_프롬프트_가이드.md`, 디자인은 `design-styles/README.md` 및 해당 DESIGN 문서, Cover는 `COVER.md`, SNS는 `SNS_업로드_문구_가이드.md`를 추가 적용한다. 이 가이드들도 통합 지침에 요약되지 않았다는 이유로 생략하지 않는다.

## 1. 전체 제작 프로세스

```
주제 선정 → Wiki_시장 관련 자료 제한 조사 → 공식자료 교차검증 → 영상 기획/대본·Scene 설계
→ 사용자 승인 → 기준 이미지 → Flow/Veo → Remotion 조립
→ TTS → 통합 QA → 최종 렌더 → 사용자 승인
→ Cover 제작·승인 → SNS 업로드 문구 작성·승인
→ 최종 자산 정리 → Git commit/push → 작업기록 마무리
```

- 조사와 기획을 먼저 끝내고, **사용자 승인 전에는 제작 단계로 넘어가지 않는다.**
- 영상, Cover, SNS 문구는 각각 별도로 승인받은 뒤에만 다음 단계로 넘어간다. 순서를 건너뛰지 않는다.
- 첫 1~2초 Hook을 최우선으로 설계하고, 한 영상은 하나의 핵심 질문·메시지에 집중한다. 한 Scene에는 한 메시지를 우선한다. 첫 1~2초 기준은 운영가이드 §3의 기존 1~3초를 최신 사용자 승인으로 변경한 규칙이다.
- TTS(발화) 문구와 화면 자막(무음 시청 대비 요약)은 반드시 별도로 작성한다. TTS 실제 발화 시간을 기준으로 Scene 길이를 잡는다.
- 자막은 의미 단위로 줄바꿈하며 최대 2줄을 기본으로 한다.
- 실제 제품 사진과 승인된 Canonical Reference를 AI 생성 이미지보다 항상 우선한다.
- 이미지·영상 생성은 승인된 기준 이미지와 구도를 바탕으로 최소 횟수만 진행하며, **사용자가 명시적으로 요청하기 전에는 이미지를 생성하지 않는다.**
- 생성 이미지 안에 자막·한글·라벨·로고를 굽지 않고 Remotion 후편집으로 처리한다.
- Flow/Veo는 꼭 필요한 최소 모션에만 사용한다. 정보형 화면·자막·비교·수치·그래픽은 Remotion을 우선한다.
- 실사/Flow 영상이 포함된 Scene은 Remotion으로 직접 캡처(video-in-video)하지 않는다. (1) 자막/박스를 투명 PNG로 Remotion still 렌더 → (2) ffmpeg로 원본 영상에 오버레이+TTS mux 순서로 처리한다. 여러 Scene 합치기는 Remotion 통합 렌더보다 ffmpeg concat을 기본값으로 하되, 실제 통합 렌더에서 스터터가 확인되지 않으면 굳이 우회하지 않아도 된다.
- 최종 Remotion 조립 전 공통 엔딩의 컴포넌트, 영상/이미지 자산, TTS/오디오, 길이, 직접 참조 파일을 하나의 세트로 확인한다. 기존 승인 엔딩은 재설계하지 않고 그대로 재사용한다.

## 2. 핵심 공통 운영 규칙 (반복 검증됨)

1. 건축자재 지식(Wiki)과 영상 제작 정보를 서로 다른 문서 영역에 보관한다.
2. 실제 제품 사진/canonical reference를 생성보다 우선하고, 승인된 기준 이미지를 canonical start frame으로 보존한다. 기준 이미지 승인 전 Remotion 본 제작에 들어가지 않는다.
3. Flow 원본 오디오는 최종본에서 음소거하고, `playbackRate`는 기본 `1.0`을 유지한다. 생성 영상이 후반에 깨지면 원본을 보존한 채 마지막 안정 프레임 전까지 trim한다.
4. 전체 대본 승인 후 Scene별 TTS를 일괄 생성한다. 각 오디오는 **접미사 버전 숫자가 가장 높은 파일이 항상 최종본**이다(무접미사 파일을 최종으로 오판하지 않는다). Scene별 최종 MP3와 전체 순서를 이어붙인 `full-tts-qa`를 함께 만들어 통합 청취 승인을 받되, 실제 영상에는 Scene별 파일을 배치한다.
5. TTS 속도로 긴 대본을 억지로 맞추지 않고, 대본 자체를 먼저 압축한다.
6. 새 수정이 이전보다 나빠지면 고치지 말고 **사용자가 마지막으로 승인한 버전으로 즉시 복귀**한다.
7. 같은 생성 문제가 2회 반복되면 같은 prompt를 반복하지 않고 생성 방식·구현 수단을 바꾼다.
8. 최종본은 1080×1920, 프로젝트 FPS, H.264/AAC로 렌더하고 audio/video 전체 디코딩까지 QA한다.
9. **[재발 방지 — 표준 규칙으로 승격]** 이미지/영상 생성 결과물(테스트·반복 포함)은 예외 없이 `public/assets/images/`, `public/assets/video/`에 저장한다. `public/references/`는 이미 승인되어 여러 편에 재사용하는 canonical 자료 전용이며 진행 중 테스트본을 넣지 않는다.
10. **[재발 방지 — 최우선 규칙]** 정리 작업 시 "코드/Remotion 소스가 참조하지 않음 = 삭제 가능"이라는 판단 기준을 절대 쓰지 않는다. **Scene별 최종 영상·최종 이미지는 참조 여부와 무관하게 항상 보존 대상**이며, "영상 최종본"과 "Scene별 최종 이미지·영상"은 서로 다른 별개의 보존 대상이다. 영상 최종본만 있고 Scene별 최종본이 없어도 안 되고, 그 반대도 안 된다. **영상과 Cover가 모두 승인되기 전에는 어떤 정리(삭제/이동)도 하지 않는다.** 이 유형의 사고가 최소 2개 프로젝트(door-order-tips-v1, bathroom-door-moisture-shorts-v1)에서 반복 발생했으므로 반드시 준수한다.
11. 자막은 TTS 문구를 그대로 따르지 않는다. 무음 시청자도 자막만으로 핵심 내용을 유추할 수 있도록 화면 자막을 별도로 작성한다.
12. Preview는 버전을 `v1, v2, v3`로 증가시키며 각 버전에서 바꾼 항목만 기록하고, 무관한 수정을 한 버전에 섞지 않는다.
13. 부분 치환(sed/assert 등)이 연속으로 실패하면 텍스트를 추측하지 말고 `grep`으로 파일의 실제 현재 내용을 먼저 확인한 뒤 수정한다. 반복 실패하는 파일은 부분 치환 대신 전체 파일을 heredoc으로 재작성한다.
14. 실제 상품 정보/현장 지식이 가이드와 충돌하면 항상 실제 정보가 우선이며, 가이드 쪽을 수정 후보로 기록한다(예: 재질 구조를 코어/표면재로 정확히 구분).

## 3. 이미지·영상 생성 Visual Grammar 핵심 원칙

(상세 실패 패턴 DB와 품목별 prompt 원문은 `건축자재_AI이미지_품목별_프롬프트_가이드.md` 참고)

- 이미지 유형을 먼저 구분한다: Flow Start Frame(움직임 없이도 완성된 구조), 정보형 이미지(텍스트 최소화, Remotion 우선), 실사 현장 이미지(real camera look), 캐릭터 결합 이미지(단일 canonical reference).
- 캐릭터는 항상 단일 canonical reference 한 장만 사용한다. 여러 reference를 동시에 주면 얼굴·체형이 섞인 제3의 캐릭터가 생성된다.
- 실제 제품의 한글 인쇄·로고·규격 문자는 AI로 새로 그리지 않는다. 실제 촬영 누끼를 우선하고, 완전 보존이 필요하면 정지 이미지+Remotion 후편집으로 처리한다.
- 형상이 민감한 자재(각재, 판재 등)는 숫자 규격만으로 비율이 고정되지 않으므로 `square-section`, `length ratio`, 금지 형태(`board/plank/ribbon 금지` 등)를 함께 명시한다.
- 결함(휨, 들뜸 등)은 색상 강조가 아니라 실제 geometry로 표현한다. 색을 지워도 결함이 읽히는지 QA한다.
- 개수가 중요한 장면은 "정확히 N개, 특정 위치는 비워둠"까지 명시한다(모델이 임의로 개수를 보완하는 경향이 있음).
- Flow에 큰 제스처(팔 벌리기 등)를 생성할 때는 원본 캐릭터 대신 1.6배 여백을 추가한 패딩 버전을 사용해 프레임 잘림을 방지한다.
- 캐릭터 등 투명 배경 영상은 Remotion에서 `<OffthreadVideo transparent muted>`로만 알파가 보존된다(`<Video>` 불가). 인코딩 직후 `ffprobe`로 실제 `yuva420p`인지 확인한다.
- Veo/Flow에 실제 전달하는 생성 프롬프트는 영어로 작성한다.

## 4. Design 스타일 라이브러리 (선택 매트릭스)

콘텐츠 성격에 맞춰 아래 10종 중 1~2개를 선택해 레이아웃·타이포·색의 역할·모션 원칙만 참고한다(브랜드 화면을 복제하지 않음). 실제 제품 Canonical Reference와 공통 Visual Grammar가 항상 디자인 스타일보다 우선한다.

| 콘텐츠 유형 | 추천 스타일 |
|---|---|
| 제품 설명 / 친근한 정보 | Figma |
| 실사 / 전문 설명 | Notion |
| 수치 / 성능 / 기술 비교 | Linear |
| 시공 / 변화 / 모션 훅 | Framer |
| 프리미엄 제품 / 단일 Hero | Apple |
| 공간 / 인테리어 / 적용 사례 | Airbnb |
| 강한 기술 / 성능 / 숫자 | NVIDIA |
| 세련된 프리미엄 정보 / 비교 | Stripe |
| 가격 / 속보 / 강한 훅 | Spotify |
| 상품 / 규격 / 가격 / 구매정보 | Shopify |

한 영상 전체를 하나로 고정할 필요는 없지만(Scene별로 다른 스타일 가능), 한 Scene 안에서는 과도하게 섞지 않는다. 전체 영상의 폰트 계열, 기본 여백, 제품 표현, 브랜드 엔딩은 통일한다. 실제 사용한 스타일만 작업기록 MD에 `Main: Notion / Scene 3: Linear`처럼 기록한다.

## 5. Cover 시스템 (SNS 대표이미지)

- 영상 최종 승인 후에만 Cover를 제작한다. Cover를 위해 영상 첫 Scene, TTS, Remotion Scene을 임의 수정하지 않는다.
- 흐름: `최종 영상 승인 → Cover 제작 → 아래 표준 QA → 업로드 문구 제작 → 업로드 → 정리`

### 5.1 표준 좌표 템플릿 (전체 Cover 공통 표준 — 방염 시리즈 등 특정 콘텐츠 전용이 아니다)

이 좌표는 3개 이상의 서로 다른 콘텐츠(방염 시리즈, 도어 발주 팁, 화장실 문 습기)에서 포인트 컬러만 바꿔 반복 재사용이 확인된 **전체 Cover 공통 표준**이다. 새 에피소드마다 컬러만 콘텐츠에 맞게 정하고, 좌표는 그대로 따른다.

1080×1920 기준:

- **박스**: `(53, 341) ~ (770, 694)`, radius 36, 불투명도 92%, 배경색은 에피소드별로 선정
- **카테고리 바**: `(90, box_top-62) ~ (98, box_top-32)`
- **카테고리 텍스트**: `x=114, y=box_top-62`, Pretendard-SemiBold 30px
- **점 인디케이터**: 박스 우측 상단 `(box_right-60~48, box_top+29~41)` 활성 + `(box_right-42~30, 동일 y)` 비활성(회색)
- **헤드라인**: `x=92` 고정, 줄간격 92px, Pretendard-Black 60px, 마지막 줄만 accent 컬러·나머지는 base 컬러
- **로고**: 78×78px. 좌우 위치는 구도에 따라 가변하되, Instagram Feed Safe 안전 영역(아래 5.3) 안에 반드시 들어와야 한다.
- **DAESAN 텍스트**: 심볼 기준 x+90, y+7, Pretendard-Black 46px
- **서브텍스트("대산종합건축자재")**: 심볼 기준 x+90, y+61, Pretendard-Medium 26px

### 5.2 컬러 규칙

- 박스 배경/카테고리/포인트 컬러는 에피소드 콘텐츠와 참고 DESIGN.md 톤에 맞춰 정하되, 헤드라인 마지막 줄과 카테고리/점 인디케이터는 같은 accent 컬러 계열로 통일한다.
- **Brand Lockup(로고+DAESAN+대산종합건축자재) 색상은 카드 컬러 스킴과 무관하게 항상 로고 파일의 실측 색상을 사용한다** (`daesanlogo2.png` 실측 `#123628`). `tokens.ts`의 `daesanGreen`(`#146335`)과 미세하게 다르므로 혼용하지 않는다.
- 실제 제품 Canonical Reference와 공통 Visual Grammar가 디자인 스타일보다 항상 우선한다.

### 5.3 Feed Safe

- Instagram profile grid의 중앙 정사각형 crop은 1080×1920 원본에서 대략 `y=420~1500` 구간만 보인다. Brand Lockup을 포함한 모든 핵심 요소가 이 구간 안에 있는지 정사각 crop 렌더로 반드시 확인한다.

### 5.4 승인·정리

- 1080×1920 세로 원본과 Instagram 중앙 정사각형 crop을 함께 만들어 QA한다.
- 승인된 대산 로고 자산만 사용하고 AI로 로고를 생성하지 않는다.
- Cover는 영상 첫 Scene과 별도 자산으로 관리한다.
- 미승인 중간본은 최종 Cover 승인 후 사용자 확인을 받고서만 정리한다.

## 6. SNS 업로드 문구 규칙

최종 영상과 Cover 승인 후에만 작성한다. YouTube, Instagram, Naver Clip을 각각 별도로 작성한다.

### 6.1 본문 작성 원칙

- TTS/자막 원문을 그대로 재사용하지 않는다. 특히 Hook(Scene1)과 결론(마지막 Scene) 문구를 거의 그대로 가져오지 않는다.
- **결론 → 이유 → 적용처** 순서의 독립된 요약문으로 작성한다.
- YouTube/Instagram은 아래 프로모 블록을 본문 뒤에 넣는다. **프로모 블록에 이미 `daesan.ai`가 들어가므로, 그 위 본문에서는 daesan.ai를 중복해서 언급하지 않는다.** (Naver Clip은 프로모 블록이 없으므로 본문에 자연스럽게 `daesan.ai`를 1회 언급한다.)
- YouTube 제목을 빠뜨리지 않는다 — 영상의 확정 타이틀을 그대로 사용한다.

### 6.3 해시태그

순서: **① 영상별 핵심 키워드(제품명·재질명·브랜드/대리점명 등) → ② 대산 고정 태그 8종 → ③ Instagram만 `#릴스 #reels` 추가.**

- 대산 고정 해시태그 8종(매번 그대로 재사용): `#인테리어자재 #건축자재 #건축자재정보 #건축자재유통 #건축자재납품 #대량자재구매 #대산 #대산종합건축자재`
- 가격/비용 키워드(`#OO가격`, `#OO비용` 등)는 주제 관련성과 무관하게 **매 편 반드시 포함**한다.
- 영상에 특정 브랜드·유통망이 언급되면(예: 특정 도어 브랜드, 대리점명) 관련 해시태그를 반드시 포함한다. 재질·공법명(예: 멤브레인도어, ABS도어)도 핵심 키워드 해시태그로 포함한다.
- 해시태그 수가 부족하다고 지적받지 않도록, 영상 소재에서 뽑을 수 있는 관련 키워드를 충분히 넉넉하게 포함한다(제품명, 브랜드명, 시공/증상 키워드, 공간명 등).

### 6.4 Naver Clip

- 제목: 24자 이내.
- 설명: 본문+모든 줄바꿈+해시태그를 합산해 200자 이내이면서 **최대한 200자에 근접**하게 채운다(짧으면 관련 해시태그를 추가해 보충).
- 프로모 블록 없이 `daesan.ai`를 본문에 자연스럽게 1회 언급한다.
- 실제 측정한 제목/설명 글자 수를 문서에 표기한다.

### 6.5 기타

- Instagram 캡션에는 계정명을 텍스트로 포함하지 않는다(UI가 자동 표시).
- 지역명을 사용한 해시태그·홍보 문구는 쓰지 않는다.
- 고정댓글(YouTube+Instagram)은 질문형 문장으로 참여를 유도하고 `daesan.ai` 언급을 포함한다.

## 7. Codex/터미널 운영 원칙 (제작 도구가 Codex/터미널 조합인 경우)

- 기본값은 **터미널 직접 실행**이다. TTS 생성, ffmpeg 처리, 정지 자막/Cover 제작, 파일 정리, Git commit/push는 전부 터미널에서 직접 처리한다.
- Codex(또는 코드 실행 에이전트)는 Vertex AI 이미지 생성, Remotion 코드/애니메이션처럼 실제 코드 작성·크리덴셜이 필요한 경우에만 사용한다.
- Codex/Astra는 실행 도구로 사용하며 불필요한 탐색 도구로 사용하지 않는다. 확정된 작업에 필요한 범위만 확인한다.
- repo 전체 탐색, 동일 MD 반복 읽기, duration 반복 확인, 작업과 무관한 lint/typecheck를 하지 않는다.
- Codex에는 확정된 작업만 지시하고, `[최소모드]` 태그로 시작하는 통합 지시서(여러 작업을 한 번에 묶은 자연어 지시) 하나로 준다. 작은 수정마다 여러 번 호출하지 않고 같은 단계의 수정은 하나의 통합 지시로 묶는다.
- 사용자에게 터미널 명령어를 줄 때는 항상 한 번에 복사 가능한 단일 코드블록으로 제공한다. 긴 heredoc(`<< 'EOF'`)이 포함된 명령은 조각내지 않고 통째로 준다.
- 매 명령어는 `{ ... } | tee /dev/tty | pbcopy`로 감싸서, 터미널 출력 확인과 클립보드 복사(결과를 다시 붙여넣기 쉽게)를 동시에 처리한다.
- macOS 기본 `/bin/bash`(3.2)는 연관배열(`declare -A`)을 지원하지 않는다. `key|value` 문자열 + `while IFS='|' read` 루프로 대체한다.
- 같은 문제가 2회 반복되면 같은 방식을 고집하지 않고 구현 수단을 바꾼다(예: 부분 치환 실패 반복 시 전체 재작성으로 전환).

## 8. 정리 및 Git 규칙

- **정리 순서**: 영상 최종 승인 → Cover 최종 승인 → (필요 시) SNS 문구 확정 → 정리 → 보안검사 → commit → push.
- **최종 영상과 Cover가 모두 승인되기 전에는 실패본·임시파일 정리를 하지 않는다.**
- 정리 전 삭제(이동) 후보를 먼저 사용자에게 보고하고, **명시적 승인 없이 파일을 삭제/이동하지 않는다.**
- §2-10의 최우선 규칙(Scene별 최종본 영구 보존)을 다시 확인한 뒤에만 정리를 실행한다.
- macOS 환경에서는 영구 삭제 대신 `~/.Trash/<프로젝트>-cleanup-YYYYMMDD/`로 이동하는 방식을 기본으로 한다(복구 가능하게 유지).
- `.env`, credential, service account JSON, API key, token, private key, client secret은 절대 stage/commit하지 않는다.
- force push는 하지 않는다. push 후 `git status`와 원격 추적 상태를 확인한다.
- 정리 후 날짜형 작업기록 MD(`YY.MM.DD수정.md`)를 남기고, 실제 사용한 DESIGN.md 스타일을 Main/Scene별로 기록한다.
- Git 종료 시 working tree가 clean인지 확인한다.

## 9. 응답 방식

- 설명은 짧고 실행 중심으로 한다. 불필요하게 장황한 설명을 피한다.
- 사용자의 명령이 명확하면 바로 수행한다.
- 사용자가 명령어를 보여주고 "체크"라고 하면 누락·불필요한 부분만 검토하고, 문제가 없으면 "픽스"라고 짧게 답한다.
- 이미지 생성은 사용자가 명시적으로 요청한 경우에만 한다.

## Terminal / Astra 역할 분리

비용과 작업시간을 줄이기 위해 판단이 필요하지 않은 단순 로컬 작업은 Terminal을 우선하고, 실제 콘텐츠·디자인·구현 판단이 필요한 제작 작업은 Astra가 담당한다.

### Terminal 우선

작업 대상과 결과가 이미 확정된 단순 작업은 Terminal에서 처리할 수 있다.

- 승인된 기준에 따른 일반적인 Slim Copy
- 프로젝트 폴더 생성
- 명확히 지정된 파일 복사·이동·이름 변경
- 디렉터리 생성
- `npm ci` 등 확정된 의존성 설치
- 파일·폴더 존재 여부 및 경로 확인
- 파일 해시·동일성 확인
- 확정된 단순 명령 실행
- 판단이 필요하지 않은 공통 MD의 명확한 문구·버전 수정

Terminal은 콘텐츠 기획이나 임의 판단을 하지 않는다.

사용자에게 Terminal 실행 명령을 제공할 때는 한 번에 복사·실행 가능한 단일 코드블록으로 제공하고, 작업 완료 결과를 다시 ChatGPT에 쉽게 전달할 수 있도록 완료 보고를 마지막에 `pbcopy`로 클립보드에 복사하는 절차를 기본 포함한다.

### Astra 담당

콘텐츠 또는 구현 판단이 필요한 실제 작업은 Astra가 담당한다.

- Wiki_시장 조사 및 자료 선별
- 공식자료 교차검증
- 제작을 위한 기술적 판단
- TTS 제작 및 실제 발화시간 기반 Scene 조정
- Remotion Scene 구현·수정
- 이미지·영상 생성
- Canonical / Reference 적용 판단
- Flow / Veo 작업
- 복잡한 자산 참조 처리
- 영상 조립 및 렌더
- 영상·오디오·자막·Scene·엔딩 QA
- 오류 분석 및 구현 방식 변경
- 결과물에 영향을 주는 복합 수정

### Slim Copy

복사 기준과 대상이 이미 확정된 일반적인 Slim Copy는 Terminal을 우선한다.

보존 자산 판단, 직접 참조 분석, 코드 수정 등이 필요한 경우에는 Astra가 필요한 범위만 판단하고 Terminal이 확정된 단순 복사를 실행할 수 있다.

가능하면 `Astra 판단 → Terminal 단순 실행 → 필요 시 Astra 제작·QA`로 역할을 분리한다.

Terminal 사용 여부와 관계없이 사용자 승인 전 제작 금지, 승인 없는 삭제·이동 금지, 승인 전 정리 금지, 원본 임의 수정 금지, 민감정보 및 Git 관련 기존 안전 규칙은 그대로 적용한다.

- v2.4 (2026-09-18): 단순 로컬 작업은 Terminal 우선, 실제 제작·판단은 Astra 담당으로 역할 분리. Terminal 명령 완료 보고의 `pbcopy` 기본 포함.

### 확정 작업의 Terminal 우선 실행

Astra를 모든 제작 단계에 반복 호출하지 않는다. 이미 작업 방식·문구·파일·결과가 확정되어 추가적인 콘텐츠 판단이 필요하지 않은 작업은, 기존 실행 방법이 확인되어 있다면 Terminal을 우선한다.

Terminal에서 처리할 수 있는 확정 작업에는 다음을 포함한다.

- 승인된 Slim Copy와 정해진 파일 복사·이름 변경
- 확정된 TTS 문구의 기존 방식 재생성
- 기존과 동일한 voice / model / speed 설정의 TTS 재실행
- 확정된 자막 문구·파일 경로·버전 번호 수정
- 확정된 Scene duration / frame 값의 단순 수정
- 기존 Remotion 구조를 유지한 재렌더
- 확정된 출력 경로로의 렌더 명령 실행
- ffmpeg / ffprobe 기반 길이·해상도·fps·codec·디코딩 확인
- 파일 해시·픽셀·오디오 동일성 등 기계적 QA
- 확정된 작업 내용을 `YY.MM.DD수정.md`에 추가 기록
- Git status / 민감정보 확인 / commit / push / working tree clean 확인

단, Terminal이 처리하려면 기존 프로젝트에서 실행 방식과 대상이 명확하게 확인되어 있어야 한다. TTS 생성 스크립트, 인증 방식, Remotion composition, 출력 경로 등을 알 수 없는 상태에서 명령을 추측해서 만들지 않는다.

판단이 필요한 경우에는 Astra가 필요한 범위만 확인한다. 이후 실행 방법이 확정되면 같은 단계의 반복 작업은 가능한 한 Terminal로 넘긴다.

기본 역할 분담은 다음 흐름을 우선한다.

`ChatGPT 조사·기획 → 사용자 승인 → Astra 최초 구현/복잡한 판단 → Terminal 확정 실행·반복 수정·렌더·기계적 QA → 필요 시 Astra 재판단`

Astra를 다시 호출해야 하는 대표적인 경우는 다음과 같다.

- Wiki_시장 조사 및 자료 선별
- 공식자료 교차검증과 사실 판단
- 새로운 Scene 설계
- 새로운 Remotion 구현
- 디자인·Visual·Reference 적용 판단
- ImageGen / Veo / Flow 등 생성 작업
- 오류 원인이 불명확한 문제의 분석
- 결과물을 보고 제작 방향 자체를 변경해야 하는 QA
- 기존 방식으로 처리할 수 없는 복합 수정

반대로 문구·값·파일·실행 방법이 이미 확정된 작은 수정 때문에 Astra가 프로젝트를 다시 탐색하도록 하지 않는다.

Terminal 명령은 가능한 경우 하나의 실행 가능한 코드블록으로 제공하고 다음 순서를 기본으로 한다.

`실제 작업 실행 → 결과 검증 → 완료 보고 생성 → 마지막 pbcopy`

`pbcopy`는 단순 지시문 복사용이 아니라, 실제 Terminal 작업이 끝난 뒤 결과 보고를 사용자가 ChatGPT에 바로 전달할 수 있도록 마지막 단계에 사용하는 것을 기본으로 한다.

- v2.5 (2026-09-21): Astra는 판단·최초 구현 중심으로 사용하고, 실행 방식이 확정된 TTS 재생성·단순 코드/타이밍 수정·Remotion 재렌더·기계적 QA·Git 등은 Terminal 우선으로 병행. Terminal 명령은 실제 실행·검증 후 완료 보고를 마지막 `pbcopy`로 전달하는 방식으로 구체화.

### 대산이 기본 포즈 자산 운영
- 신규 영상 프로젝트 생성 시 승인된 대산이 기본 포즈 3종을 공통 원본에서 해당 영상 프로젝트 내부로 복사해 보존한다.
- 기본 포즈 3종:
  - `small-daesan-pose-front-v1.png` — 정면/쳐다보기
  - `small-daesan-pose-point-right-v1.png` — 오른쪽 가리키기
  - `small-daesan-pose-explain-v1.png` — 설명하기
- 영상 프로젝트에서는 공통 폴더의 원본을 직접 참조하지 않고 프로젝트 내부 복사본을 사용한다.
- 캐릭터의 얼굴, 표정, 체형, 비율, 포즈를 임의로 변형하지 않는다.
- 필요한 경우 승인된 외곽 배경 제거와 크기·위치 조정만 허용한다.
- 콘텐츠와 구도에 맞는 포즈를 선택하며, 신규 포즈 생성보다 승인된 기본 포즈 재사용을 우선한다.
